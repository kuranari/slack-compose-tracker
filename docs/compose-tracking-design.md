# 作成時間の計測と保存の設計メモ

2026-10-29 作成、2026-10-30 更新（本文と文字の履歴の記録を追加）。

## 用語と計測の定義

- **下書き**: 1 つの入力欄に入力された、送信または破棄されるまでのテキスト。
  - キーは `teamId/channelId`（チャンネル）か `teamId/channelId/threadTs`（スレッド）。
- **開始**: 入力欄が空でない状態で、最初の `input` イベントを観測した時刻。
- **終了**: 入力欄が空になったのを観測した時刻。
  - 送信操作（Enter / `Cmd+Enter` / 送信ボタン）から `SEND_WINDOW_MS`（3 秒）以内に空になれば **送信**。終了時刻は送信操作の時刻にする。
  - それ以外は **破棄**。全文を手で消した場合もここに入る。
  - `MIN_DISCARD_MS`（3 秒）未満で終わった破棄は記録しない（ユーザー指定、2026-10-30）。「あ」「＠」のような打ち始めの断片で、分析のノイズになるため。
- 経過時間の表示（入力欄右上のバッジ）と記録は、どちらも同じ「開始」を基準にする。

### 既知の割り切り

- 他のチャンネルに移っていた時間も経過時間に含まれる。
  - Slack はチャンネルごとに下書きを保持するので、戻ってきたら同じ下書きの続きとして扱う。
- 拡張機能を読み込む前からあった下書き（ページ読み込み時点で入力欄に文字がある）は、開始が不明なので次の入力から計測する。
- Threads 一覧など、URL がチャンネルを指さない画面の入力欄は追跡しない。
- スレッドを開いても URL は変わらない。`threadTs` は、スレッドペイン先頭の `[data-msg-ts]`（親メッセージ）から取る。
- `channelId` は、入力欄の入れ物（`[data-qa="message_input"]`）の `data-channel-id` を最優先で使い、取れなければ URL のチャンネルの位置を使う（2026-10-30）。スレッドではその間に、親メッセージの `data-msg-channel-id`、URL の `/thread/<チャンネルID>-<ts>` も試す。
  - アクティビティ画面では URL が `/client/T…/activity-inbox` のままで、選んだ会話が中央に開く。入れ物の `data-channel-id` は、この画面でも送信先の会話の ID になっていた（実機で確認）。
  - アクティビティや検索の画面では、URL のチャンネルの位置が `activity-inbox` や `search` になる。Slack の下書きはスレッドごとに 1 つで、どの画面から開いても同じものが出る。画面ごとに別の下書きとして扱うと、アクティビティで書き始めてチャンネル側で送ったとき、送信を取りこぼす。さらに、アクティビティ側の下書きが残り続け、後でその画面を開いたときに破棄として記録されていた。

| ---------------------- | ------------------------- | ----------------------------- | -------------------------- | ------------------------------ |
| 実装コスト             | ◎                         | ○                             | △ 権限の再取得の UI が必要 | × ホストプログラムの配布が必要 |
| ファイルとして扱えるか | ×                         | ○ 手動で書き出す              | ◎ 自動                     | ◎ 自動                         |

**採用: B**（ユーザー確認済み）。まずは手軽さとテストのしやすさを優先した。

### 記録の粒度

| 案                       | 長所                             | 短所                                                |
| ------------------------ | -------------------------------- | --------------------------------------------------- |
| キー入力ごとの生イベント | 後から定義を変えて集計し直せる   | 1 日数千件で `storage.local` の 10MB をすぐ使い切る |
| **下書き単位（採用）**   | 小さい。表示と同じ定義で一貫する | 開始・終了の定義を変えても過去分は再計算できない    |

折衷として、下書き単位の記録に `inputCount` と `length` も残している。

#### 2026-10-30 追記: 本文と文字の履歴

「送ったメッセージを CSV で見たい」「数秒ごとの文字の履歴から書き直しの癖を直したい」という要件が加わった。下書き単位はそのままにして、次の 2 つを足した。

- `text`: 送信または破棄の直前の全文
  - 絵文字は `<img>` で描画されて `innerText` に出ないので、`:pray:` のような表記に置き換える（2026-10-30）。入力欄を複製して画像を置き換え、画面外の自前の Shadow DOM に置いて `innerText` を読む。Slack の入力欄そのものは書き換えない。
- `snapshots`: `{ at: 開始からの ms, text: 全文 }` の配列
  - 最初の入力（`at: 0`）、`SNAPSHOT_INTERVAL_MS`（10 秒、ユーザー指定）ごとに本文が変わっていたとき、最終形、の 3 種類。
  - 直前と同じ本文は重複させない。

| 案                                         | 長所                                      | 短所                               |
| ------------------------------------------ | ----------------------------------------- | ---------------------------------- |
| キー入力ごとの差分                         | 書き直しを完全に再現できる                | 量が多い。IME の途中経過まで混ざる |
| **一定間隔の全文スナップショット（採用）** | 単純で壊れにくい。AI に渡しても読みやすい | 間隔内の細かい書き直しは見えない   |

- 破棄した下書きも本文と履歴を残す（ユーザー確認済み）。送らなかった下書きも、癖を見る手がかりになるため。
- **履歴には IME で確定した文字だけを残す**（ユーザー確認済み）。
  - 理由：変換中の「にほんご」が履歴に入ると、次の履歴で「日本語」に変わったとき、ただの変換が書き直し（削除＋挿入）として数えられる。書き直しの率などの分析にノイズが入る。
  - 方法：`compositionstart` / `compositionend` で入力欄ごとに変換中かを覚えておく。変換中は履歴を見送り、確定後の最初の観測で取る。変換中に始まった下書きは、最初の履歴（`at: 0`）も確定後に取る。
  - 開始時刻は、変換中でも最初のキー入力のまま（変換中の入力も作成時間に含める）。
  - 割り切り：変換を確定しないまま長く入力し続けると、その間の履歴は取らない。再変換などの「変換に迷った癖」は見えない。変換中に破棄した場合、`text` と最後の履歴には未確定の文字が残りうる。
  - **比較用に、変換中も含む履歴（`rawSnapshots`）も並行して残す**（ユーザー判断。どちらが癖を見るのに向くか、使いながら決めるため）。同じ 10 秒間隔で、変換中かどうかに関係なく取る。分析ツールは `--raw` で切り替えられる。容量はおよそ倍になるが、`unlimitedStorage` なので許容する。どちらかに決まったら、もう一方はやめてよい。
- 本文は平文でローカルに保存し、書き出したファイルにも入る（ユーザー確認済み）。書き出し先の `data/` は `.gitignore` 済みで、コンソールのログにも本文は出さない。
- 1 件が大きくなるので、`unlimitedStorage` を付けた。さらに、記録を日付ごとのキー（`records:YYYY-MM-DD`）に分け、1 回の get→set を小さく保っている。
- 書き出しは、AI での分析用の JSONL（履歴込み）と、表で見る用の CSV（本文込み、履歴は含まない）。

### 書き込みの経路

- content script → `runtime.sendMessage` → background → `storage.local`。
- 書き込むのは background だけで、`appendRecord` の中で get→set を直列化している。複数タブから同時に追記しても取りこぼさないため。
- popup は読み取り専用。

## 層の分け方

| ファイル                 | 層               | 責務                                                                |
| ------------------------ | ---------------- | ------------------------------------------------------------------- |
| `lib/slack-dom.ts`       | IO（Slack DOM）  | セレクタと DOM の探索。Slack の変更で壊れたら直すのはここだけ       |
| `lib/draft-session.ts`   | ドメイン（純粋） | 開始・終了・送信か破棄かの判定                                      |
| `lib/compose-record.ts`  | ドメイン（純粋） | 記録の型、集計、CSV 変換                                            |
| `lib/duration.ts`        | 純粋             | 表示用の時間フォーマット                                            |
| `lib/record-store.ts`    | IO（storage）    | 永続化                                                              |
| `lib/elapsed-badge.ts`   | IO（UI）         | バッジの描画。Shadow DOM に fixed 配置し、Quill の DOM には触れない |
| `entrypoints/content.ts` | 組み立て         | イベントの購読、定期チェック、各層の接続                            |

## テスト

- 単体テスト（`npm test`）：純粋な関数と、`fakeBrowser` を使った保存処理。
- E2E（`npm run e2e`）：本物の Slack に対して Playwright で動かす。
  - 自分宛て DM に実際にメッセージを送る（1 回で 4 件）。送信キーは「`Cmd+Enter` で送信」の設定を前提にしている。
  - ログイン状態は専用のプロファイル（`e2e-profile/`）に保存する。初回だけ `npm run e2e:login` で手動ログインする。
  - 日本語入力は、CDP の `Input.imeSetComposition` で変換中の状態を作って再現する。確定の Enter が `isComposing=true` で届くことも、テストの中で確かめている。
  - 本物を使うのは、Slack の DOM との一致を保証するため。模倣ページは使わない（ユーザーの選択）。
  - **既定はヘッドレスで動かす。** 画面を出すと、ウィンドウとフォーカスを奪ってユーザーの作業の邪魔になるため。ヘッドレスでも Slack、拡張の読み込み、CDP での IME の再現がすべて動くことを確認済み（2026-10-30）。動きを目で追いたいときだけ `E2E_HEADED=1` を付ける。手動ログイン（`e2e:login`）は、人が操作するので画面を出す。

## 見直す条件

- 記録が数万件を超えて `storage.local` の容量や読み込み速度が問題になったら、IndexedDB に移すか、古い記録を間引くことを検討する。
- 書き出しを手で行うのが負担になったら、C（File System Access API）を検討する。
- 「離席時間を除いた実作業時間」が欲しくなったら、`lastInputAt` を使ったアイドル判定を追加する。その場合は記録の型の変更も検討する。
