# 配布方式の検討メモ

2026-10-30 時点。**結論: A（手元でビルドしたものを読み込む）**。配布対象は自分だけで、プライベート用と業務用の 2 台で使う（ユーザー確認済み）。

## 前提

- Chrome 拡張（Manifest V3、WXT）。権限は `storage`、`unlimitedStorage`、`https://app.slack.com/*` へのコンテンツスクリプト。
- **Slack のメッセージ本文（送信しなかった下書きを含む）と、10 秒ごとの文字の履歴をローカルに保存する。** 外部への送信は無い。配布方式を選ぶうえで、これが一番重い制約になる。
- 現状は `version: 0.0.0`、アイコンは WXT の雛形のまま。名前は "Slack Compose Tracker"。

| 観点                       | A. ビルド済み zip を手で読み込む | B. Web ストア（限定公開）                      | C. Web ストア（一般公開）        | D. Web ストア（Workspace ドメイン限定） | E. 自前ホストの CRX ＋ 企業ポリシー |
| -------------------------- | -------------------------------- | ---------------------------------------------- | -------------------------------- | --------------------------------------- | ----------------------------------- |
| 対象                       | 自分と数人の技術者               | URL を知っている人                             | 誰でも                           | 自社の Google Workspace のユーザー      | 管理下の端末                        |

補足:

- A：手で読み込んだ拡張は自動更新されない。ストア外の CRX ファイルは、企業ポリシー（E）を使わない限り、Windows と macOS の Chrome では基本的にインストールできない。なので A は「フォルダを読み込む」形になる。
- B、C、D：ストアでは、ユーザーの個人的なやり取りを扱う拡張として、データの扱いの申告とプライバシーポリシーの URL が求められる。拡張の名前に "Slack" を含めると商標の扱いが問題になりうるので、"Compose Tracker for Slack" のような形への改名も要検討。
- Firefox：WXT は `npm run build:firefox` に対応しているが、今は対象外。

## 判断の軸

1. **配布する相手**：自分だけ ／ 同僚数人 ／ 社内全体 ／ 一般。これでほぼ決まる。
2. **会社の承認**：業務の Slack の本文をローカルに保存するツールを、社内に配ってよいか。
3. **更新の頻度**：試行錯誤の段階では A の方が速い。安定したら自動更新の価値が上がる。
4. **ストアのアカウント**：個人の開発者アカウントで出すか、会社のアカウントで出すか。

## どれを優先するなら、どれを選ぶか

| 優先すること                       | 選ぶ案                       |
| ---------------------------------- | ---------------------------- |
| すぐ使える・手間ゼロ（自分と数人） | A                            |
| 同僚に気軽に配り、自動更新もしたい | B                            |
| 社内に正式に展開し、管理したい     | D（Workspace が無ければ E）  |
| 広く公開したい                     | C（先に B で運用実績を積む） |

## 結論

**A を採用。** 配布対象が自分だけなので、ストアの審査、プライバシーポリシー、改名、zip の配布はどれも不要。自動更新が無い欠点も、開発者本人が使うので問題にならない。

### 2 台で使うための判断

- **業務用の端末の規程**: デベロッパーモードでの読み込みと、業務用の Slack の本文をローカルに保存することは、問題ないことをユーザーが確認済み。
- **記録は端末ごとに分けたままにする**（ユーザー確認済み）。業務用と私用は分けて見たいので、同期はしない。どのみち `chrome.storage.sync` は約 100KB で、本文と履歴は入らない。
- **拡張機能の ID を固定する**（`wxt.config.ts` の `manifest.key`、ID は `andgbpomldibkaoklgpnnomddfmdhfpj`）。
  - 手で読み込んだ拡張の ID は本来フォルダのパスで決まり、storage も ID ごとに分かれる。固定しないと、リポジトリの場所や開発用/本番用ビルドの違いで、記録が別の拡張のものになる。
  - 公開鍵は manifest に入れてコミットする。秘密鍵は `keys/`（gitignore 済み）に置く。手で読み込む用途では秘密鍵は使わないので、無くしても困らない。
  - 同じ ID の拡張は同時に 1 つしか読み込めない。各端末では本番用か開発用のどちらか 1 つだけを読み込む。
- **拡張機能を削除すると記録も消える。** 大事な記録は、ポップアップから JSONL で `data/` に書き出しておく。書き出した JSONL は、専用ページから取り込み直せる（重複は除く）。

### 運用手順

各端末での初回:

1. `git clone` → `npm install` → `npm run build`
2. `chrome://extensions` でデベロッパーモードをオンにし、`output/chrome-mv3` を読み込む

更新するとき（各端末）:

1. `git pull` → `npm install` → `npm run build`
2. `chrome://extensions` で拡張機能の再読み込みボタンを押し、開いている Slack のタブを再読み込みする

開発する端末だけは、`output/chrome-mv3` の代わりに `output/chrome-mv3-dev` を読み込み、`npm run dev` を動かしておく。ID が同じなので、記録はそのまま引き継がれる。

ID を固定する前に読み込んでいた拡張の記録は、次の手順で移す（1 回だけ）:

1. 古い拡張のポップアップから JSONL を書き出す
2. 古い拡張を削除し、ID を固定したビルドを読み込む
3. 専用ページの「インポート」から、書き出した JSONL を取り込む

### 参考（当初の暫定案）

- 配布対象が同僚に広がったら B に移す。本文を扱う拡張なので、一般公開（C）より先に、限定公開で運用実績を積む。
- その場合に必要になる準備: バージョン番号の運用、アイコンと名前の見直し（"Slack" の商標）、開発用ログの整理、データの扱いの説明文、記録を消す手段。

## 見直す条件

- 配布対象が変わったとき（例：自分だけ → チーム）
- 外部への送信を伴う機能（同期、AI API の呼び出しなど）を足すとき。審査とプライバシーの前提が変わる。
